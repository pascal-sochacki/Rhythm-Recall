# Rhythm Recall

A chart-free [FeedBack](https://github.com/got-feedBack/feedBack) minigame for guitar and bass. Listen to two bars, then play the same rhythm on **any note**. The click stays on through the handoff. Only attacks in the reply count; no pitch, fret, string or sustain grading.

## Install and play

1. Place this directory in **your installation’s** `plugins/rhythm_recall` (or its configured external plugin directory). Keep `plugin.json`, `game.js` and the entire `assets/` directory together. FeedBack must serve `/api/plugins/rhythm_recall/assets/onset-processor.js` as JavaScript. Reload/restart FeedBack and enable the bundled Minigames framework. No build, npm install, CDN or separate server component.
2. Select guitar or bass in FeedBack. In a browser, use HTTPS or localhost, grant microphone permission, and select an explicit device and channel in the **Note Detection** plugin. On Desktop, configure the primary instrument input and channel in host Input Setup.
3. Open **Minigames → Rhythm Recall**. Check the displayed input, choose 40–150 BPM (default **80**), and confirm. On Desktop the confirmation explicitly names Electron capture. Use headphones and a clean DI: a microphone hearing the click will grade the click as your playing.
4. Follow the two-bar attack grid in 4/4. The higher click marks beat one of each bar. The lower pitched example notes stop for both reply bars; keep playing against the metronome. Course mode works through eight named phrases, from quarters to rests, offbeat eighths, gallops, sixteenths and the 3–3–2 tresillo. Master a phrase with **at least 80% on two of its last three replies** (two successes immediately suffice). The next example starts on the next downbeat. After the last pattern the course cycles again until you leave.
5. **Weak patterns first** starts with the lowest lifetime accuracy among patterns tried on this instrument, breaking ties by fewer attempts. On mastery it selects a different weak pattern. Without history it starts at the first pattern. Use the course to introduce all patterns. Pause releases the input; review/confirm to resume at the beginning of the example. Completed replies remain saved. Backgrounding, active input failure or a setup change discards the partial reply.

## How a reply is measured

The metronome and example tones are scheduled at absolute times on the capture `AudioContext` clock. A 20 ms timer queues the next 100 ms; it does not generate the beat. Every phrase begins with the same quarter note, so that beat can already be scheduled while the preceding reply’s final corrected input frame is being scored. A stalled scheduler or missing callback fails visibly rather than silently skipping beats or grading a broken take.

The AudioWorklet detector looks for an energy rise above a decaying envelope in 128-sample windows, with a 45 ms retrigger guard. It sends batches of onset frame numbers and the processed frame range, never PCM. Even a silent input sends progress; missing or discontinuous input does not count as rests. Each corrected attack belongs to the half-open reply interval `[start, end)`; an early first attack during the example is **not** borrowed. Within that interval the closest attack in each target’s window wins. Each attack/target is used at most once. Windows are capped at ±95 ms and ±44% of the local subdivision and nearest target spacing. Unmatched targets are misses; unmatched attacks (including duplicates or notes in rests) are extras. Accuracy = `hits / (hits + misses + extras)`. There are no points for filling silence.

**Input delay** shifts processing timestamps, not the click. Positive ms subtracts delay from detected attacks; negative ms moves them later. Try steady quarters and inspect **signed** error: for consistently +40 ms late, try +40 ms more correction and compare. The mean absolute error measures spread from the target without early/late cancellation. Both timing measures use matched attacks only; large errors may instead appear as a miss plus an extra. This is manual compensation, not hardware latency measurement. Device/output changes may require a new setting.

**Local practice history** shows completed-reply counts, hits/misses/extras and timing by named phrase, plus the same totals by recurring beat motif (attempts there count beat occurrences). Extras belong to the beat where they were played. Scores are aggregated across tempos separately for guitar and bass in this origin’s `localStorage` key `rhythm_recall.progress.v1`. Clearing that key resets progress. No PCM, device IDs, accounts, XP or public runs are saved. If storage is unavailable or malformed, the UI reports memory-only practice rather than overwriting it. The host hub’s own profile/leaderboard chrome is not this history.

## Host integration and capture limits

Read-only source check: FeedBack `eef58c8`, Note Detection `412433d`, Desktop `00653cf`. Capture/lifecycle conventions follow the sibling MIT-licensed Fretboard Recall plugin.

- Core `plugins/__init__.py` derives `has_script` and serves the manifest script at `/api/plugins/<id>/screen.js`; the JS loader injects the scoped stylesheet from `assets/`. The Minigames registry discovers `plugin.json.minigame`. We use the direct or pending JS registration path. The framework’s stage Quit normally calls `end()`, submitting a run even at zero. Rhythm Recall intercepts that click in capture phase and navigates home; the host’s `screen:changed` teardown closes the stage **without** `end`, `submitRun` or a summary. No framework globals are patched.
- **Is there already a timestamped pick feed?** Not a chart-free, pitch-independent, selected-input stream on the inspected public Minigames API. `scoring.createContinuous` emits *pitch estimates* with analysis `tMs`; its mic fallback can open the default device. Discrete/chord scoring wraps a chart detector. `static/capabilities/note-detection.js` reports hit/miss/verdict diagnostics, not raw attacks. Desktop *does* have an internal sample-indexed spectral-flux `OnsetDetector`, but `getNoteVerdicts()` returns chart-specific judgments in song time. Optional `detectNotes()` exposes per-**pitch** `onsetSeq`/`onsetMs` snapshots, not a timestamped queue of every pick on the Web Audio clock. A polled raw ring is not a sequenced capture tap. This game doesn't start the native engine, install a chart, claim independent pitch onsets are individual picks, or poll the ring.
- Browser capture reads `slopsmith_notedetect.deviceId/channel`. Desktop reads `audio.getCurrentDevice()` and `audio.listSources()` and requires an active primary source (`id=0`, `deviceKey=0`) plus **one exact, nonblank input label match** in Electron’s enumeration. It shows driver, label and channel before opening. No default/communications alias, fuzzy match, new device picker or settings writes. Exact device ID constraints, returned track ID and available channel count are checked, plus track label on Desktop. Mono averages the available first pair; left/right selects channel 1/2. The capture worklet has no outputs; only synthesized tones are audible from this plugin. Any host monitoring is unaffected.
- Rechecking identity during acquisition and periodically while playing catches selection changes. Pause, Quit and navigation disconnect private nodes, stop scheduled voices and tracks, close the context, and cancel the owner’s timers. Late permission grants are stopped, not adopted by a new stage. Native IDs and Electron IDs are different namespaces: a name match **cannot prove physical identity**. Hidden labels, duplicated names, unavailable settings, exclusive/ASIO-only devices, denied permission and unsupported channels must fail; configure an explicitly exposed input and retry. No OS-default substitution.
- The worklet’s `currentFrame` is the first frame of a render block, **not an ADC timestamp**. Attack frames and the exclusive end of the analyzed input are converted to seconds at the context sample rate and shifted by the same manual delay. Message arrival time does not determine attack timing. A secure context and working AudioWorklet support are required; a missing or failed module stops capture rather than falling back to main-thread processing. A running silent interface cannot distinguish a disconnected cable from rests. Quiet fingerstyle attacks, legato, compressed/distorted signals, string noise, monitor bleed and driver processing can miss or double-trigger. There is no claim of calibrated accuracy or hardware validation.

## Tests / hardware checklist

Run `npm test` (Node 20+; built-in test runner, no install). The shipped worklet runs in a VM against synthetic bass/guitar plucks, silence and variable block lengths. Core tests cover grids, bounded matching, rests/extras, mastery, weak ranking and audio scheduling across phrase changes. Capture/lifecycle mocks exercise channel routing, timestamp correction, identity, cancellation, processor failure, teardown, registration and Quit. With the host checkout at `../../got-feedBack/feedBack` or `FEEDBACK_HOST_DIR=/path/to/feedBack`, the optional smoke test executes its **actual JS loader and Minigames framework** in a VM, checking script/CSS URLs, deduplication, stage start, capture-phase Quit and navigation without submission. DOM, HTTP and hardware are mocked. This is not a full server/install or physical-device test.

Before release, verify on a real guitar **and** low bass: select left/right separately; try weak and strong attacks, sustained notes and muted rests; check the two-bar handoff at slow/fast tempos; calibrate with headphones; confirm no example notes during reply and no monitoring echo. On Desktop also try duplicate labels, permission denial, exclusive native routing and concurrent capture. Change device/channel, unplug, background, pause and quit during the permission prompt and during playing. Confirm the mic indicator stops and only completed replies reappear after reload.
